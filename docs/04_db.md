# DB設計

Valiark の **valiark-dev** など単一 Supabase プロジェクトに複数アプリを載せる前提で、Panda Talk のドメイン表は `panda_` 接頭辞とする（`auth.users` は全アプリ共通）。

## テーブル一覧

### panda_profiles
```sql
id            UUID PRIMARY KEY REFERENCES auth.users(id) -- Supabase Auth UID
email         CITEXT UNIQUE          -- Appleログインではnullの可能性あり
username      CITEXT NOT NULL UNIQUE -- ユーザーが設定する一意のID
name          TEXT NOT NULL
avatar_url    TEXT
bio           TEXT
created_at    TIMESTAMP DEFAULT NOW()
updated_at    TIMESTAMP DEFAULT NOW()
```

### panda_questions
```sql
id            UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id       UUID REFERENCES panda_profiles(id)
text          TEXT NOT NULL
option_a      TEXT NOT NULL
option_b      TEXT NOT NULL
category      TEXT
created_at    TIMESTAMP DEFAULT NOW()
updated_at    TIMESTAMP DEFAULT NOW()
```

### panda_answers
```sql
-- ENUM定義（public.answer_choice）
CREATE TYPE answer_choice AS ENUM ('a', 'b');

id            UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id       UUID REFERENCES panda_profiles(id)
question_id   UUID REFERENCES panda_questions(id)
choice        answer_choice NOT NULL
created_at    TIMESTAMP DEFAULT NOW()

UNIQUE (user_id, question_id)
```

### panda_friendships
```sql
id         UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_a_id  UUID REFERENCES panda_profiles(id)
user_b_id  UUID REFERENCES panda_profiles(id)
requested_by UUID REFERENCES panda_profiles(id) -- 申請したユーザー
status     TEXT NOT NULL DEFAULT 'pending'  -- 'pending' | 'accepted'
created_at TIMESTAMP DEFAULT NOW()
accepted_at TIMESTAMP

UNIQUE (user_a_id, user_b_id)
CHECK (user_a_id < user_b_id)   -- UUIDの大小で順序固定 → 逆方向レコードを物理的に防ぐ
```

**設計方針:**
- INSERT前にUseCase側で `user_a_id < user_b_id` になるよう並び替える
- 申請者は `requested_by` に保持する（user_a_id/user_b_idは順序固定のため申請方向を表さない）
- 申請時は `status = 'pending'`
- 承認時は `status = 'accepted'`
- 断る・解除する場合はレコードを削除
- 友達一覧は `status = 'accepted'` かつ自分が `user_a_id` または `user_b_id` のレコードを取得
- 1ペア1レコードが保証されるためBからAへの重複申請はDB側で防げる

### panda_match_scores
```sql
id                  UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_a_id           UUID REFERENCES panda_profiles(id)
user_b_id           UUID REFERENCES panda_profiles(id)
match_rate          FLOAT NOT NULL       -- 0.0 ~ 1.0 （インデックス用に保持）
common_answer_count INT NOT NULL
same_answer_count   INT NOT NULL
display_score       FLOAT                -- match_rate * common / (common + 50)
updated_at          TIMESTAMP DEFAULT NOW()

UNIQUE (user_a_id, user_b_id)
CHECK (user_a_id < user_b_id)   -- UUIDの大小で順序固定 → 1ペア1レコード保証
```

**更新時:** `same_answer_count` と `common_answer_count` を+1し、`match_rate = same / common` を再計算して保存

**設計方針:**
- ユーザーペアごとに1レコード（nC2件）
- 共通回答が0問のペアはレコードを作らない
- マッチ画面は単純な `SELECT ... ORDER BY display_score` で取得できる

**更新タイミング（インクリメンタル更新）:**
- ユーザーAが問題Qに回答した瞬間に、問題Qに回答済みの全ユーザーとのスコアを差分更新
- バッチ再計算は不要

**レコード数の目安:**
| ユーザー数 | 最大レコード数（実際はもっと少ない） |
|---|---|
| 1,000人 | 約50万 |
| 10,000人 | 約5,000万 |

※ 共通回答がないペアはレコードなしなので実際はnC2より大幅に少ない

### panda_groups
```sql
-- ENUM定義
CREATE TYPE group_type AS ENUM ('high_match', 'middle_match', 'low_match');

id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
name        TEXT NOT NULL
type        group_type NOT NULL
created_at  TIMESTAMP DEFAULT NOW()
```

**グループ種別:**
| type | 概要 | 人数 |
|---|---|---|
| high_match | 全ペアの合致度が高い | 3人 |
| middle_match | 全ペアの合致度が50%付近 | 3人 |
| low_match | 全ペアの合致度が低い（真逆） | 3人 |

**グループ成立条件:** 3人全ペア（3C2=3組）が該当の合致度範囲に収まっていること

### panda_group_members
```sql
id         UUID PRIMARY KEY DEFAULT gen_random_uuid()
group_id   UUID REFERENCES panda_groups(id)
user_id    UUID REFERENCES panda_profiles(id)
created_at TIMESTAMP DEFAULT NOW()

UNIQUE (group_id, user_id)
```

### panda_messages
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
group_id    UUID REFERENCES panda_groups(id)
user_id     UUID REFERENCES panda_profiles(id)
body        TEXT NOT NULL
created_at  TIMESTAMP DEFAULT NOW()
```

### panda_comments
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
question_id UUID REFERENCES panda_questions(id)
user_id     UUID REFERENCES panda_profiles(id)
choice      answer_choice NOT NULL  -- どっち派のコメントか
body        TEXT NOT NULL
created_at  TIMESTAMP DEFAULT NOW()
```

**設計方針:**
- 表示時はuser_idを出さず匿名表示
- choiceで「a派のコメント」「b派のコメント」に分けて表示できる
- 1ユーザーが同じ問題に複数コメント可能（制限するなら UNIQUE (question_id, user_id) を追加）

### panda_direct_messages
```sql
id            UUID PRIMARY KEY DEFAULT gen_random_uuid()
sender_id     UUID REFERENCES panda_profiles(id)
receiver_id   UUID REFERENCES panda_profiles(id)
body          TEXT NOT NULL
created_at    TIMESTAMP DEFAULT NOW()
```

### panda_push_tokens
```sql
id         UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id    UUID REFERENCES panda_profiles(id)
token      TEXT NOT NULL        -- FCM / APNsトークン
platform   TEXT NOT NULL        -- 'ios' | 'android'
updated_at TIMESTAMP DEFAULT NOW()

UNIQUE (user_id, token)
```

**設計方針:**
- 1ユーザーが複数デバイスを持てる（UNIQUE制約で管理）
- ログアウト時にレコード削除
- トークンのローテーション時は `updated_at` を更新
- プッシュ通知は Firebase Cloud Messaging（FCM）を初期から採用
- `panda_notifications` INSERT → Supabase Database Webhook → Edge Function → FCM API → iOS(APNs)/Android

### panda_notification_settings
```sql
user_id                  UUID PRIMARY KEY REFERENCES panda_profiles(id)
likes_enabled            BOOLEAN DEFAULT TRUE
comments_enabled         BOOLEAN DEFAULT TRUE
friend_requests_enabled  BOOLEAN DEFAULT TRUE
matches_enabled          BOOLEAN DEFAULT TRUE
groups_enabled           BOOLEAN DEFAULT TRUE
messages_enabled         BOOLEAN DEFAULT TRUE
updated_at               TIMESTAMP DEFAULT NOW()
```

**設計方針:**
- 設定画面の通知ON/OFFをユーザー単位で保持する
- panda_push_tokensはデバイス単位、panda_notification_settingsはユーザー単位で管理する

### panda_question_likes
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id     UUID REFERENCES panda_profiles(id)
question_id UUID REFERENCES panda_questions(id)
created_at  TIMESTAMP DEFAULT NOW()

UNIQUE (user_id, question_id)
```

**設計方針:**
- いいね数は `SELECT COUNT(*) FROM panda_question_likes WHERE question_id = ?` で集計
- Hotタブのソートに利用（いいね数 + コメント数で「盛り上がり度」を算出）。集計ビューは `panda_hot_questions`。

### panda_comment_likes
```sql
id         UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id    UUID REFERENCES panda_profiles(id)
comment_id UUID REFERENCES panda_comments(id)
created_at TIMESTAMP DEFAULT NOW()

UNIQUE (user_id, comment_id)
```

**設計方針:**
- いいね数は `SELECT COUNT(*) FROM panda_comment_likes WHERE comment_id = ?` で集計
- コメント一覧取得時にいいね数も一緒に返す。集計ビューは `panda_comment_summaries`。

### panda_notifications
```sql
-- ENUM定義
CREATE TYPE notification_type AS ENUM (
  'like',            -- 自分の質問にいいねされた
  'comment',         -- 自分の質問にコメントされた
  'friend_request',  -- 友達申請が来た
  'friend_accepted', -- 友達申請が承認された
  'new_match',       -- 高合致ユーザーが現れた
  'group_created'    -- グループに追加された
);

id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id     UUID REFERENCES panda_profiles(id)   -- 受信者
actor_id    UUID REFERENCES panda_profiles(id)   -- 通知を起こしたユーザー（NULLはシステム通知）
type        notification_type NOT NULL
target_id   UUID                        -- 対象レコードのID（question_id / group_id など）
is_read     BOOLEAN DEFAULT FALSE
created_at  TIMESTAMP DEFAULT NOW()
```

**設計方針:**
- 未読件数は `SELECT COUNT(*) WHERE user_id = ? AND is_read = false`
- 既読化は `UPDATE SET is_read = true WHERE user_id = ? AND is_read = false`
- actor_idがNULLの場合はシステム通知（グループ自動生成など）

## インデックス設計（重要）

```sql
-- username検索
CREATE INDEX idx_panda_profiles_username_prefix ON panda_profiles (LOWER(username::text) text_pattern_ops);

-- 診断フィード
CREATE INDEX idx_panda_questions_created_at ON panda_questions(created_at, id);

-- 合致度の高速検索
CREATE INDEX idx_panda_match_scores_user_a_display ON panda_match_scores(user_a_id, display_score DESC);
CREATE INDEX idx_panda_match_scores_user_b_display ON panda_match_scores(user_b_id, display_score DESC);

-- 回答の検索
CREATE INDEX idx_panda_answers_question_choice ON panda_answers(question_id, choice);

-- 友達一覧
CREATE INDEX idx_panda_friendships_user_a_status ON panda_friendships(user_a_id, status);
CREATE INDEX idx_panda_friendships_user_b_status ON panda_friendships(user_b_id, status);

-- いいね数集計
CREATE INDEX idx_panda_question_likes_question_id ON panda_question_likes(question_id);
CREATE INDEX idx_panda_comment_likes_comment_id ON panda_comment_likes(comment_id);

-- コメント取得
CREATE INDEX idx_panda_comments_question_created_at ON panda_comments(question_id, created_at DESC, id DESC);

-- お知らせの未読取得
CREATE INDEX idx_panda_notifications_user_id_unread ON panda_notifications(user_id, is_read, created_at DESC);
```

**方針:**
- 初期はMVPで頻繁に使う検索条件に絞る
- 投稿者別、カテゴリ別、DM履歴、グループチャット、push token管理などは、実クエリが重くなってから追加する
- `panda_answers` は `UNIQUE (user_id, question_id)` が user_id 検索にも効くため、別途 `panda_answers(user_id)` は作らない
