# DB設計

Valiark の **valiark-dev** など単一 Supabase プロジェクトに複数アプリを載せる前提で、Panda Talk のドメイン表は `panda_` 接頭辞とする（`auth.users` は全アプリ共通）。

**スキーマの正本:** `supabase/migrations/202605130001_initial_schema.sql`（ENUM・テーブル・制約・トリガー・初期ビュー・RLS 有効化）→ `202605130002_auth_helpers.sql`（`get_user_by_email`）→ `202605130003_rename_users_to_panda_profiles.sql`（旧 `public.users` からのリネーム移行用。001 から `panda_profiles` で始まる環境では実質 no-op）→ `202605140004_prefix_panda_domain_tables.sql`（テーブル／ビューを `panda_*` にリネーム）。本ドキュメントはこの順序で適用したあとの **`public` 上の Panda ドメイン** と一致させる。

### panda_friendships
```sql
id             UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_a_id      UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
user_b_id      UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
requested_by   UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE  -- 申請したユーザー（user_a / user_b のどちらか）
status         public.friendship_status NOT NULL DEFAULT 'pending'
created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
accepted_at    TIMESTAMPTZ

UNIQUE (user_a_id, user_b_id)
CHECK (user_a_id < user_b_id)   -- UUIDの大小で順序固定 → 逆方向レコードを物理的に防ぐ
CHECK (requested_by IN (user_a_id, user_b_id))
CHECK (
  (status = 'accepted' AND accepted_at IS NOT NULL)
  OR (status = 'pending' AND accepted_at IS NULL)
)
```

**設計方針:**
- INSERT前にUseCase側で `user_a_id < user_b_id` になるよう並び替える
- 申請者は `requested_by` に保持する（user_a_id/user_b_idは順序固定のため申請方向を表さない）
- 申請時は `status = 'pending'`
- 承認時は `status = 'accepted'`
- 断る・解除する場合はレコードを削除
- 友達一覧は `status = 'accepted'` かつ自分が `user_a_id` または `user_b_id` のレコードを取得
- 1ペア1レコードが保証されるためBからAへの重複申請はDB側で防げる

### panda_match_scores
```sql
id                  UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_a_id           UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
user_b_id           UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
match_rate          DOUBLE PRECISION NOT NULL   -- 0.0 ~ 1.0
common_answer_count INT NOT NULL               -- > 0
same_answer_count   INT NOT NULL               -- 0 .. common_answer_count
display_score       DOUBLE PRECISION GENERATED ALWAYS AS (
                      match_rate * (common_answer_count::double precision / (common_answer_count + 50))
                    ) STORED
updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (user_a_id, user_b_id)
CHECK (user_a_id < user_b_id)
CHECK (match_rate >= 0 AND match_rate <= 1)
CHECK (common_answer_count > 0 AND same_answer_count >= 0 AND same_answer_count <= common_answer_count)
```

**更新時:** `same_answer_count` と `common_answer_count` を+1し、`match_rate = same / common` を再計算して保存（`display_score` は DB が生成列で維持）

**設計方針:**
- ユーザーペアごとに1レコード（nC2件）
- 共通回答が0問のペアはレコードを作らない
- マッチ画面は単純な `SELECT ... ORDER BY display_score` で取得できる

**更新タイミング（インクリメンタル更新）:**
- ユーザーAが問題Qに回答した瞬間に、問題Qに回答済みの全ユーザーとのスコアを差分更新
- バッチ再計算は不要

**レコード数の目安:**
| ユーザー数 | 最大レコード数（実際はもっと少ない） |
|---|---|
| 1,000人 | 約50万 |
| 10,000人 | 約5,000万 |

※ 共通回答がないペアはレコードなしなので実際はnC2より大幅に少ない

### panda_groups
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
name        TEXT NOT NULL          -- CHECK: btrim(name) <> ''
type        public.group_type NOT NULL
created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
```

**グループ種別:**
| type | 概要 | 人数 |
|---|---|---|
| high_match | 全ペアの合致度が高い | 3人 |
| middle_match | 全ペアの合致度が50%付近 | 3人 |
| low_match | 全ペアの合致度が低い（真逆） | 3人 |

**グループ成立条件:** 3人全ペア（3C2=3組）が該当の合致度範囲に収まっていること

### panda_comments
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
question_id UUID NOT NULL REFERENCES panda_questions(id) ON DELETE CASCADE
user_id     UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
choice      public.answer_choice NOT NULL  -- どっち派のコメントか
body        TEXT NOT NULL          -- CHECK: btrim(body) <> ''
created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
```

**設計方針:**
- 表示時はuser_idを出さず匿名表示
- choiceで「a派のコメント」「b派のコメント」に分けて表示できる
- 1ユーザーが同じ問題に複数コメント可能（制限するなら UNIQUE (question_id, user_id) を追加）

### panda_direct_messages
```sql
id            UUID PRIMARY KEY DEFAULT gen_random_uuid()
sender_id     UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
receiver_id   UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
body          TEXT NOT NULL          -- CHECK: btrim(body) <> ''
created_at    TIMESTAMPTZ NOT NULL DEFAULT now()

CHECK (sender_id <> receiver_id)
```

### panda_push_tokens
```sql
id         UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id    UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
token      TEXT NOT NULL        -- FCM / APNs 等（CHECK: btrim(token) <> ''）
platform   public.platform NOT NULL
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (user_id, token)
```

**設計方針:**
- 1ユーザーが複数デバイスを持てる（UNIQUE制約で管理）
- ログアウト時にレコード削除
- トークンのローテーション時は `updated_at` を更新
- プッシュ通知は Firebase Cloud Messaging（FCM）を初期から採用
- `panda_notifications` INSERT → Supabase Database Webhook → Edge Function → FCM API → iOS(APNs)/Android

### panda_question_likes
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id     UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE
question_id UUID NOT NULL REFERENCES panda_questions(id) ON DELETE CASCADE
created_at  TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (user_id, question_id)
```

**設計方針:**
- いいね数は `SELECT COUNT(*) FROM panda_question_likes WHERE question_id = ?` で集計

**設計方針:**

- コメント一覧取得時にいいね数も一緒に返す。集計ビューは `panda_comment_summaries`。

### panda_notifications
```sql
id          UUID PRIMARY KEY DEFAULT gen_random_uuid()
user_id     UUID NOT NULL REFERENCES panda_profiles(id) ON DELETE CASCADE   -- 受信者
actor_id    UUID REFERENCES panda_profiles(id) ON DELETE SET NULL         -- 起案者（NULL はシステム通知）
type        public.notification_type NOT NULL
target_id   UUID                        -- 対象レコードのID（question_id / group_id など）
is_read     BOOLEAN NOT NULL DEFAULT false
created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
```

`notification_type` の意味付けは上記「ENUM 型」表のとおり（`like` = 自分の質問にいいね、など）。

**設計方針:**
- 未読件数は `SELECT COUNT(*) WHERE user_id = ? AND is_read = false`
- 既読化は `UPDATE SET is_read = true WHERE user_id = ? AND is_read = false`
- actor_idがNULLの場合はシステム通知（グループ自動生成など）

### Row Level Security と関数

- **`202605130001_initial_schema.sql` 末尾:** 次のテーブルに `ENABLE ROW LEVEL SECURITY`（適用直後の名前。`202605140004` で `questions`→`panda_questions` 等にリネーム）: `panda_profiles`, `questions`, `answers`, `friendships`, `match_scores`, `groups`, `group_members`, `messages`, `comments`, `direct_messages`, `question_likes`, `comment_likes`, `notifications`, `push_tokens`, `notification_settings`。
- **`202605130002_auth_helpers.sql`:** `public.get_user_by_email(text) returns uuid`（`SECURITY DEFINER`、`SET search_path = public`）。`anon` / `authenticated` / `public` から `EXECUTE` を revoke。
- **`20260516140000`:** `get_user_by_email` をメールの大小無視で検索（後続マイグレーションで `lower(trim(...))` 形式に更新される場合あり）。
- **`20260516150000_get_user_by_provider_ids.sql`:** `get_user_by_apple_id(apple_sub)` / `get_user_by_line_id(line_uid)` — `auth.users.app_metadata` の `apple_id` / `line_id` で既存ユーザーを引く（Edge の LINE / Apple ネイティブ認証で、**メール表現だけでは同一利用者を判別できない**ため）。`service_role` のみ `EXECUTE`。

## インデックス設計（重要）

```sql
-- username検索
CREATE INDEX idx_panda_profiles_username_prefix ON panda_profiles (LOWER(username::text) text_pattern_ops);

-- 診断フィード
CREATE INDEX idx_panda_questions_created_at ON panda_questions(created_at, id);

-- 合致度の高速検索
CREATE INDEX idx_panda_match_scores_user_a_display ON panda_match_scores(user_a_id, display_score DESC);
CREATE INDEX idx_panda_match_scores_user_b_display ON panda_match_scores(user_b_id, display_score DESC);

-- 回答の検索
CREATE INDEX idx_panda_answers_question_choice ON panda_answers(question_id, choice);

-- 友達一覧
CREATE INDEX idx_panda_friendships_user_a_status ON panda_friendships(user_a_id, status);
CREATE INDEX idx_panda_friendships_user_b_status ON panda_friendships(user_b_id, status);

-- いいね数集計
CREATE INDEX idx_panda_question_likes_question_id ON panda_question_likes(question_id);
CREATE INDEX idx_panda_comment_likes_comment_id ON panda_comment_likes(comment_id);

-- コメント取得
CREATE INDEX idx_panda_comments_question_created_at ON panda_comments(question_id, created_at DESC, id DESC);

-- お知らせの未読取得
CREATE INDEX idx_panda_notifications_user_id_unread ON panda_notifications(user_id, is_read, created_at DESC);
```

**方針:**
- 初期はMVPで頻繁に使う検索条件に絞る
- 投稿者別、カテゴリ別、DM履歴、グループチャット、push token管理などは、実クエリが重くなってから追加する
- `panda_answers` は `UNIQUE (user_id, question_id)` が user_id 検索にも効くため、別途 `panda_answers(user_id)` は作らない
